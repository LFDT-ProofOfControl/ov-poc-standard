# Review: the draft is broken at issuance

**Frank Dylan Rosario**  
**Dr. Lin Wang**  
**Dr. Octavia Sulea**

6 November 2026

Academic review of Working Draft v0.1 of *Open Verification: the Proof-of-Control Standard for Agents* [1]. Informative. The published draft remains the normative text under `0.1/en/`. This review states why the architecture fails in the object it issues, and why every later control is a new name for that same exposed token, together with a new way for the agent to copy it or leak it.

## Abstract

The Standard presents a control architecture that is fixed by the object it issues. That object, as the identity chapter states it and as the figure draws it, is a signed, short-lived, scoped delegation token given by a principal to an agent, with every later action supposed to trace back to that principal [8]. What the figure actually places in the world is an unguarded token. The agent receives it, holds it, and carries it. From the moment of issuance onward the agent has a series of ordinary mechanisms — its own memory, the tool call, the prompt and the context window, the approval screen, the message to a second agent, the evidence row, the log it can read back — by which that token can be copied, echoed, stored, or sent onward. Expiry, scope, a gateway, a measurement, a single-use flag, and a tier arrive later as new labels on the same object. The secret set remains in the agent and remains presentable for a later act. The primitive this relabeling never reaches is a proof of knowledge of a witness, bound to the bytes of this act, and burned before the checker accepts.

## 1. The architecture is fixed by the object it issues

A control architecture is fixed by the object it issues. The draft's object, as it is stated in the identity chapter and drawn in the figure, is this picture: a principal issues a signed, short-lived, scoped delegation token to the agent, and every action is supposed to trace to that principal. The figure's own caption, in [C5 Identity](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md), says it without ornament:

> The identity chain: principal issues a signed, short-lived, scoped delegation token to the agent; every action traces back to the principal.

That sentence is the architecture. What it places in a running system is an unguarded, exposed token, issued to the agent. The agent receives it. The agent holds it. The agent is thereafter the program that can copy it, log it, put it on a wire, drop it into a prompt, hand it to a second agent, or write it into a row the agent can read back. Short life and narrow scope are words printed on the token. They tell a later checker how long the token works and which audience it names. They do not take the token out of the agent's hands, and they do not make a second presentation impossible. For as long as the clock allows, and inside the label the token carries, the same object authorizes this command and the next one. Everything the draft builds after the figure is a ceremony around that exposed token.

The chapter states its objective in the same breath. It asks for "verifiable evidence of actors, agents, and delegated authority relationships" and for "evidence that every action traces to a legitimate principal," and it names the verifiable facts as "which agent and which principal ran" ([C5, control objective](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md)). Then it tells the implementer how the trace is to be achieved:

> Cryptographic principal-to-agent delegation tokens (e.g., short-lived OAuth/JWT, W3C DIDs, or cryptographic capability URLs) explicitly bind agent tool calls back to human intent.

The word "explicitly" is the false claim. A token on a tool call binds the call to whoever is holding the token. Human intent is not in the token. The principal's name is a field. The agent's process is the holder. Binding a call to a field inside an object the agent can read is not a binding to a person who answered these bytes. It is a binding to a bearer. The draft calls that bearer a chain of identity. The chain is the exposed object, passed along.

The requirements then enumerate the copies the agent is instructed to touch. [C5.1.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) says: "Verify that the agent authenticates with a cryptographic credential (certificate, key pair, or DID) validated before actions execute, and that credential-validation events are recorded." The agent holds the certificate, the key pair, or the DID. The private key is in the agent's reach, because the agent is the party that must authenticate. The validation event is a record of that presentation, and a pipeline that stores the credential material beside the event has made a second copy. [C5.1.3](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) says: "Verify that each agent tool call carries a delegation token (short-lived OAuth/JWT, W3C verifiable credential, or capability URL) issued by or on behalf of the principal, cryptographically linking the call to the principal's grant." The token rides on the call. The wire is a copy. The retry buffer is a copy. The gateway log is a copy. The auditor is told to "decode a sampled tool call's token" and check issuer, audience, expiry, and linkage. Decoding is possible because the token was placed, in the clear of the protocol, on the call the agent sent. [C5.1.4](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) moves "the agent's identity credential" so that it is "bound to an attested execution environment (key held in the attested enclave or TPM)." The room changes. The holder does not. The agent process inside a matching measurement is still the process that presents the key, and it can still write the resulting presentation into the context that leaves the room. [C5.2.1](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) says agent-to-agent messages "are signed by the sending agent's credential." The signing key stays with the sender, so the sender can sign as many bodies as it wishes, and any of those bodies can carry the delegation token. [C5.2.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) tells the receiver to validate the sender "using published key material, without contacting the sender's operator." The published half is public. The private half remains in the agent. A genuine signature on a leaked token is not a forgery. It is the exposed object arriving in a new set of hands.

At every one of those steps the agent has numerous mechanisms, all of them ordinary, by which to copy the token or leak it. It can assign the token to a variable in the process that will run the next tool. It can write it into a debug line. It can place it in the context that will be sent to the model on the next turn, so that the inference itself is now attending over the secret. It can include it among the fields of a tool result the model will see again. It can put it in a workspace file, a memory note, or a retrieved chunk. It can render it, or a session derived from it, on an approval screen the agent controls. It can sign it into a message to a second agent. It can leave it in an evidence row if the pipeline stored what the checker used. None of these is an exploit against the design. They are uses of an object the design issued to the agent and then required the agent to present.

The failure is earlier than a prompt injection, earlier than a second agent, and earlier than a thief. Those parties succeed because the first design decision already put the authorizing secret where the running program can read it. The threat vocabulary records the consequence and then sets it aside. On `identity-abuse` it says the threat is "an agent claims authority it was not granted," that Proof-of-Control addresses "cryptographic identity" and "binds every action to a principal," and that "credential theft or social engineering at the human level" is out of scope ([THREATS.md](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/docs/use-cases/THREATS.md)). Theft is a second way to obtain what the legitimate holder was given on purpose. The agent does not need to steal the token. The token was issued to the agent. An injected instruction does not need a new secret either. `prompt-injection` is defined as crafted input that "redirects the agent's objective," and the vocabulary's out-of-scope line is "the injection itself" ([same table](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/docs/use-cases/THREATS.md)). The redirected objective spends the token already resident in the process. `system-prompt-leakage` is stated as "Not addressed." The prompt and the token sit in the same context. A disclosure of one and a disclosure of the other are neighboring writes.

Keep the payment in view, because the figure's promise should be watched against bytes. The command is `pay invoice 1042 for 20 units from account A to account B`. A principal has issued a delegation token whose scope includes payments and whose expiry has not arrived. The agent places that token on the tool call. A checker validates signature, expiry, audience, and scope, which is exactly the validation [C4.2.1](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md) demands: "each action's signed authorization token is cryptographically validated (signature, expiry, audience, scope) before execution, and that validation results are recorded." The record names the principal already written inside the token, which is what [C5.1.1](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) asked for. Minutes later the agent, still inside the same window and still holding the same token, places it on a second call whose bytes are `pay invoice 1042 for 20000 units from account A to account B`. The same checks pass. The figure's promise, that every action traces to the principal, is satisfied on paper for both amounts, because both calls carried the object the principal issued. Nothing in the issuance asked whether a witness bound these bytes. The twenty-unit payment and the twenty-thousand-unit payment are the same architecture, working.

[C4 Authorization](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md) announces a different sentence and then returns to the same object. The chapter opens:

> Authority is scoped to the action, not to the actor: permission tied to the specific operation, its configuration, and its limits at the time it acts cannot be replayed against a different action.

The requirements written under that sentence do not implement it. [C4.1.5](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md) says: "Verify that agent credentials are issued per task with scope and expiry bound to that task (e.g., short-lived tokens), and that no standing broad-scope credential is available to the agent at runtime." Read the sentence carefully. It forbids a standing broad credential. It does so by issuing another credential and making that credential available to the agent at runtime. The actor holds the permission. The action later presents it. The twenty-unit call and the twenty-thousand-unit call share the task token whenever the task was defined widely enough to cover both, and the draft leaves that width as an out-of-scope question. `excessive-agency` says the threat is that "the agent can do more than its task needs," and that "whether the grant was too broad" is out of scope ([THREATS.md](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/docs/use-cases/THREATS.md)). The chapter that claimed permission cannot be replayed against a different action has delegated the meaning of "different" to a scope string the agent is holding.

The false claim of security is the claim that adding steps to this process makes the token safe. The draft's own introduction says the quiet part about cost and then calls the cost trustworthiness. Under "Industry-led" it says "the strongest verification is usually the most expensive," and that "the gain in trustworthiness at the top comes with a real jump in cost" ([introduction](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/docs/introduction.md)). The jump is real. The trustworthiness is not, because each added step re-inspects the same exposed token. Count what a single tool call must survive if the stack is implemented as written, on the path the model is waiting on.

The call carries the delegation token, and someone decodes issuer, audience, expiry, and linkage ([C5.1.3](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) auditor note). The agent authenticates with its credential, and a validation event is recorded ([C5.1.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md)). If the deployment claims the higher identity level, an attestation of the enclave or TPM is consulted ([C5.1.4](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md)). The action is evaluated against the granted permission set, and the evaluation record names the permission matched ([C4.1.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md)). Tool-call parameters are validated against a registered schema, and a parameter digest is stored ([C4.1.4](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md)). The evaluation is path-aware, so "the evaluated context for each invocation includes parameters and state carried from upstream invocations in the same execution path" ([C4.1.7](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md)). Each hop of a delegation chain "carries the delegator's signature, and the full chain validates back to the originating principal" before the authority is exercised ([C4.2.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md)). Where the chain is hidden, the relying party instead verifies a zero-knowledge credential presentation ([C4.2.4](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md)). All of that is still the token, inspected more times.

Then the evidence chapter puts a synchronous machine in front of the tool. The figure in [C7](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C07-Evidence-Generation-and-Properties.md) is captioned: "the agent acts through the out-of-band Action Interception Gateway, which emits evidence before, during, and after each tool call." [C7.1.1](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C07-Evidence-Generation-and-Properties.md) requires that gateway to be "a separate process or service from the agent," so every tool effect takes a network hop. [C7.1.2](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C07-Evidence-Generation-and-Properties.md) requires three evidence records per action — before, during, and after — "each independently signed." [C7.1.3](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C07-Evidence-Generation-and-Properties.md) makes the durable write a precondition of release: "the gateway does not forward the action to the tool until the before record is durably written." The inference loop is stalled on a log. [C7.1.4](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C07-Evidence-Generation-and-Properties.md) may then mint "a single-use capability cryptographically bound to the evaluated snapshot digest," which is a new bearer the agent or the call must present, or it may keep "the credentials and transport for the effect" inside the attesting environment with the agent. Complexity has been added. The secret has been renamed, and in one of the options it has been put back in the agent's room.

This is a false claim of security by accumulation. Each new predicate — expiry, audience, scope, schema, path context, chain walk, zero-knowledge wrapper, gateway hop, three signatures, a durable write — is offered as another reason to believe the token. None of them asks whether a witness bound the bytes of this act. The inference system pays for all of them. The model context is asked to carry the token, the grant, the approval sentence, the upstream parameters, and the evidence identifiers, because [C4.1.7](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C04-Authorization.md) grows the evaluated context with every upstream call and because [C5.1.3](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C05-Identity.md) puts the token on the call the model is in the middle of making. Context length on the hot path grows with the number of tools. The token, which is a secret, occupies the same attention budget as the prompt. That is both a leak, as the earlier mechanisms of copy described, and a tax on the inference itself. The draft's "Speed" principle does not answer this. It says the industry is "moving faster than any standards process," and that "the risk here is arriving late, not arriving imperfect" ([introduction](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/docs/introduction.md)). Speed, in the draft, is a remark about the editing calendar. The runtime the draft specifies is the opposite of fast. It serializes every tool effect on a remote gateway, a chain validation, and a durable write.

A high-performance computing network is built for the other shape. The fabric moves small messages at a fixed cost. A production inference service on that fabric can afford a constant piece of work per act: bind these bytes, burn a nonce, accept or refuse, and leave nothing reusable in the context for the next act. It cannot afford a design whose per-act work grows with delegation-chain depth, with the number of upstream tool calls stuffed into the next context, and with three signed records flushed to a durable store before the tool is allowed to run. Elegance, in that environment, is constant work and no authorizing secret retained in the inference loop. The draft has neither. Its top tier is defined as the expensive tier, and [C8](https://github.com/LFDT-ProofOfControl/ov-poc-standard/blob/main/0.1/en/0x10-C08-Verifiability-Tiers.md) records the state of the evidence for the whole ladder: "The evidence base is five self-authored deployment descriptions and no real-world system." A stack that has not been shown on a real system, and whose conformant hot path is a durable write plus a chain walk plus a growing context, lacks the elegance to operate in production on a high-performance network. Adding more checks of the same token will not create that elegance. It will add more latency to the inference path and more copies of the secret the figure already handed to the agent.

The architecture is fatal at the start in this precise sense. Authority was defined as presentation of a secret the agent holds. No downstream check can recover a different authority from that definition. Downstream checks can add a clock, a label, a gateway, a measurement, a chain walk, three signatures, and a grade. They overburden the inference system with that accumulation, and they call the accumulation security. The exposed token remains the thing that is presented. The twenty-unit payment and the twenty-thousand-unit payment still pass together, inside one lifetime, on one object, after every one of those checks has been paid for.

## 2. Each later stage renames the token and gives the agent another way to copy it

The object is stable. The names change. At every step along the path the agent has numerous ordinary mechanisms by which the token, the key, or the decision bit can be copied or leaked. The mechanisms are not exotic. They are the places the draft itself tells the agent to touch the secret.

**Issuance, under the name delegation token.** The token arrives in the agent as an OAuth token, a JWT, a verifiable credential, or a capability URL [8]. It resides in process memory, in the configuration the runtime loaded, or in the secret store the agent is allowed to read because the agent is the client. The agent can assign it to a variable, write it into a debug line, place it in the context that will be sent to the model on the next turn, or include it among the fields of a tool result that the model will see again. Any of those copies is a second bearer. The original remains valid until expiry. The copy remains valid for the same interval, because a bearer is verified by what it is, not by which buffer held it.

**Authentication, under the name credential.** C5.1.2 has the agent hold a certificate, a key pair, or a DID [8]. The private key is the secret that makes the token believable. The agent process that signs with it can also export what it can read, log a signing request that includes the material, or pass a handle to a tool whose arguments are then stored in the transcript. The validation log the requirement demands is another copy of the fact of presentation, and if the pipeline stores the credential material beside the validation result, the log is a copy of the secret itself. A later reader of that row, including the agent, holds what the row stored.

**Attestation, under the name of a key in an enclave or a TPM.** C5.1.4 moves the credential into an attested environment so that a machine whose measurement misses the reference cannot exercise it [8]. The agent process that runs inside a matching measurement is still the process that presents the key. The room has changed. The holder has not. Inside that room the agent can still place the resulting presentation on a tool call, and can still write the presentation into the context that leaves the room. A matching measurement is a predicate on the platform. It records that the room looked right. It does not burn the act, and it does not stop the process inside the room from copying the presentation onto the next call.

**Runtime, under the name per-task credential.** C4.1.5's task token sits in the agent for the life of the task [6]. A task that lasts minutes is a window in which every tool call the agent chooses can carry the token. The agent copies it forward by the simplest means there is: it remembers it. Context, a memory write, a retrieved note, or a file in the workspace are all memories. `memory-poisoning` in the vocabulary is concerned with whether a memory write has a provenance [9]. A validly stored copy of the task token is a clean write of an exposed secret. The token then steers the next decision because it is present, not because anyone tampered with the note.

**The tool call, under the name authorization token.** C4.2.1 validates signature, expiry, audience, and scope of the token the call carries, and records the result [6]. C5.1.3 already required the token to be on the call [8]. So the wire itself is a copy. Proxies, gateway logs, retry buffers, and the tool's own receipt each receive the bytes. A retry inside expiry resends them. The 20-unit payment, logged with its token, can be submitted again from the log. The second submission matches the same signature, the same audience, and the same scope. The draft's expiry check passes for both, because expiry is the lifetime of the exposed object, not a consumption of it.

**The approval, under the name approval record.** C4.1.6 stores the approver, the exact content presented, the decision, and a timestamp [6]. The agent is the program that composes the screen and the program that composes the tool bytes. It can show a person the sentence "pay invoice 1042 for 20 units," store that sentence as the content presented, and submit 20,000 units with the same delegation token. It can also hold the approver's session if the approval interface lives in the agent's reach, and it can write the decision bit into the transcript. `approval-fatigue` says the Standard evidences the intent presented and the decision, and leaves human fatigue and social engineering out of scope [9]. The copy here is the split between the sentence and the bytes. Both can be stored. Only one of them needs to be true for the record to look complete.

**Release, under the name single-use capability.** C7.1.4 says the gateway may release a capability bound to a snapshot digest and a target resource [7]. The agent composed the snapshot. The capability comes back to the caller or rides with the call. Until it is spent, it is another bearer, and the agent can copy it into the same places it copied the delegation token: memory, a retry, a second tool, a message. "Single-use" is a flag the checker is asked to honor. The bytes are still in the agent's hands before the flag is consulted. C7.1.4's other option places the effect credentials inside the attesting environment that emits the request [7]. If the agent runs in that environment, the effect secret and the agent share the room, and a leak is a write from that room to anywhere the agent can send a string.

**The message to another agent, under the name of the sender's credential.** C5.2.1 has the agent sign with its credential. C5.2.2 has the receiver check the signature from published keys, without calling the sender's operator [8]. The private key stays with the sender, so the sender can sign as many messages as it wishes. The body of the message can carry the delegation token, the task token, or the capability. The second agent then holds a copy. It can present that copy under C4.2.2's delegation chain, store it, or pass it one hop further [6]. `insecure-inter-agent-comms` worries about forged messages [9]. A genuine signature on a leaked token is not a forgery. It is the exposed object moving to a new holder, exactly as a bearer is designed to move.

**The confidential chain, under the name of a zero-knowledge presentation.** C4.2.4 allows the relying party to receive a proof of policy-compliant delegation that can be checked without seeing the chain [6]. The agent is the party that produces the presentation. What it produces, it can produce again from the same underlying secret, and it can store the presentation artifact itself. The encoding changed. The ability to present again did not. An assessor who is pleased by the words "zero knowledge" has been shown a new wrapper on the issuance the figure already drew.

**The evidence row, under the name of the execution record.** C5.1.1 requires the record to carry the agent identifier and the principal identifier [8]. C2.4.1 asks for minimized forms of protected data [13]. Minimization is a hope about fields. If the pipeline stores the token, the credential configuration, or the capability because the checker used them, the row is a copy, and the agent that can read its own record can read the copy. `data-exfiltration` says the Standard gates unauthorized egress and treats the in-scope call as the authorized case [9]. An in-scope call is a call that presents the reusable set. The agent leaks the token by doing the thing the architecture told it to do: it puts the token on a call that the scope allows, including a call whose purpose is to send data outward. `system-prompt-leakage` is stated as not addressed at all [9]. The prompt is another secret sitting in the same process, and the token is often sitting in the same context as the prompt. A disclosure of the prompt and a disclosure of the token are neighboring writes.

**The grade, under the name Tier 3 or Tier 4.** C8 says Proof-of-Control exists at those tiers [10]. The tier grades the evidence it is given. The evidence is the renamed token and the log of its presentations. A high tier on this stack is a formal pass on the exposed object. It certifies the copies.

Appendix B offers the last rename. Signature, verifiable credential, remote attestation, commitment, zero-knowledge proof: these are filing labels for the inventory [1]. An assessor who files the delegation token under any of them has obeyed the menu. The agent still holds the secret the label describes.

## 3. One reusable set, carried from stage to stage

These are not separate secrets that happen to coexist. They are one set, because each stage's output is the next stage's input, and the agent is standing at every stage with the ability to read, assign, log, and forward.

The set is the private key, the bearer token, the session that follows a successful check, the capability URL, the approval decision, the snapshot capability, and every copy of those values that has been written into context, memory, a tool argument, a peer message, or an evidence row. C5.1.3 puts the token on the call the agent sends [8]. C4.1.5 leaves the task credential in the runtime [6]. C7.1.1 puts a gateway in the path and says the agent reaches tools through it [7]. The gateway is a hop the bytes pass through. Logs on that hop are copies. C7.1.4 then either returns a capability or keeps the effect credential in the environment with the agent [7]. In both arrangements the agent has a mechanism of access.

C7.3.2 tries to lift one key out of the set. Evidence records are to be signed by keys the gateway holds, with operator identities and agent identities kept off those keys [7]. That sentence protects the log key. It does not protect the delegation token, the agent key, the task credential, or the capability. A log the agent cannot re-sign is still a log of secrets the agent can present, and if the row contains those secrets the agent can read them back. Integrity of the record multiplies the reusable set. It gives the copies a signature.

The threat table watches this set move and then places the possession problem outside the chapter that would have to solve it. `identity-abuse` builds a cryptographic identity and leaves credential theft out of scope [9]. `excessive-agency` records what authority was exercised and leaves the breadth of the grant out of scope [9]. `prompt-injection` gates the resulting action and leaves the injection itself out of scope [9]. The injection does not need a new secret. It needs the secret already resident in the process, and the draft has spent an entire identity chapter putting it there. The vocabulary and the requirements agree on the arrangement: the secret set belongs in the agent, and a misuse of it is filed as someone else's concern.

## 4. The patches leave the exposed token where it was

The later requirements are remedial predicates. Each one can be implemented exactly and the token remains presentable. Each one also adds a surface on which a copy can rest.

**Expiry and scope.** The identity chapter calls the token short-lived and scoped [8]. C4.1.5 repeats the demand for the task [6]. Picture the 20-unit payment at 10:01 and the 20,000-unit payment at 10:04, both inside a token whose expiry is 10:15 and whose scope says payments. Both presentations are what the predicates asked for. The agent did not break expiry. The agent used the window the issuance created, and it could copy the token into a retry buffer at 10:02 so that a replay at 10:09 is the same object working as specified. A clock is not a burn.

**The approval slip.** The record of approver, content, decision, and time is a new artifact beside the token [6]. It gives the agent a second string to keep: the sentence shown to a person. That sentence can be logged, resent, and stored as if it were the command. The tool bytes travel separately, with the delegation token attached. The patch has created two copies of "what was authorized," and they are not required to be the same bytes. A witness bound to the command would have made the second copy fail. The slip does not.

**The gateway and the before-record.** C7.1.1 inserts a process between agent and tool [7]. C7.1.3 says the before-record is written, and then the action is forwarded [7]. The token crosses the gateway, so the gateway's log is a copy, and the before-record is a copy of the decision to forward. C7.1.4's single-use capability is a new bearer minted from that decision [7]. The agent can hold the capability, include it in a second request, or describe it in a message, until some checker spends it. The hole was presentation. The patch added a checkpoint that checks a presentation and sometimes issues a fresh one.

**Attestation.** The enclave or TPM gives the key a room [8]. Logs, context windows, and tool arguments are doors out of the room. The agent inside the room can open them, because the agent is the program the room was built to run. The secret has a new address and the same ability to be copied onto the wire.

**Path checks.** C4.1.7 carries upstream parameters into the next evaluation, and C4.1.8 says a diagnostic output must not raise an approval threshold [6]. These are filters on a chain. The first call still presented the exposed token, and the parameters of that call — including any secret the agent chose to place in an argument — become the upstream context of the next call. The path check can then bless a wider command because the widened bytes arrived as context from a call the token already authorized. The first presentation funds the chain. The filter reads the chain.

**The tier.** Tier 3 asks an outsider to check the evidence. Tier 4 asks the release to follow the check. Proof-of-Control is those two grades [10]. Point them at this stack and the outsider checks the renamed token, and the release follows the renamed token. The grade is the last patch. It does not withdraw the secret. It publishes a pass on the secret, which is a further copy, this time in the conformance claim a buyer will read.

Taken in order, the patches are an avoidance. At each hole the draft could have taken the authorizing secret off the path and demanded a proof of this act's bytes. It adds a label instead: short-lived, scoped, per-task, single-use, attested, gateway-mediated, tiered. The labels are the relabeling. The cryptographic act remains the presentation of a secret the agent can copy.

## 5. The primitive the relabeling never reaches

There is a plain primitive, older than this draft, that does not hand the agent a reusable authorizing secret. For this act, a prover shows knowledge of a witness. The showing binds the canonical bytes of this act, a fresh nonce, and the identity of the checker. The ledger burns the nonce before the checker accepts. The witness is not among the outputs. The released view is the challenge, the masked response, and one terminal decision [2]. The next act requires a new showing. A signature on a token, a credential presentation, and a measurement of a platform do something else. They show that a holder presented a reusable object and that the object's predicates matched. They leave the object in the holder's hands for the next presentation.

One-shot is that primitive on interactive steps, which is the right shape for the payment. Interactive step 1 is the 20-unit command. The allocator reserves the step. The proof binds those exact bytes. The ledger burns the nonce before the checker accepts. The 20,000-unit command is interactive step 2, which means a new reservation, a new binding, and a new burn. There is no task token sitting in the agent that can fund step 2, because step 1's authority ended when step 1's nonce was burned. The API protocol implements this path as challenge, respond, validate, and ledger nonce burn [5]. Future-time reservation and the service check of the request hash are still being formalized [5]. The shape of the requirement is already visible in the burn.

Oscillation is the same primitive placed between two service processes, which is the right shape when a billing service speaks to a payment service and the payment service speaks back. The billing service binds the 20-unit message. The payment service burns that nonce before it accepts the message. The reply is a new act, with its own nonce. A later amount is a new direction, not a second use of the first message's secret. The geometric account specifies the alternation and the separate allocation per direction [4]. The protocol marks the continuous tunnel as proposed and partial [5]. The primitive does not wait on that tunnel. The one-shot burn is already the requirement the draft's renames do not state.

PassPlus is the on-device form of the checker. A pinned guest issues a challenge and returns one decision on the bearings. A local grant is written when the decision is accept. The enrollment plaintext is sealed. The Authority's rows hold hashes and sealed bytes, so the witness is not the thing a log browser recovers [3]. The clients run that ceremony. What they do not yet do is halt a payment tool on the burn. That placement is the gateway the draft thought it was building, pointed at the proof instead of at the token. A deployment can copy the draft's words — single-use, before-record, bound snapshot — and still burn a bit the caller supplied. On the PassPlus Authority path, consume stores `proof_ok` from the caller and stores true when the caller sends the nonce alone [3]. That stored true is another rename, a decision bit standing where a proof should have been. The burn that replaces the architecture is the burn of a proof of these bytes, checked by an anchored checker, with the witness unreleased [2] [5].

Under that primitive the agent's mechanisms of copy change their meaning. The agent can still log, remember, and forward. What it logs is a challenge, a masked response, and a decision on bytes that have already been burned. A copy of that record does not authorize the 20,000-unit payment. A copy of the draft's token does.

## 6. Full conformance reproduces the exposed token

Assume every remedial sentence is implemented with discipline. Tokens are short. Scope is narrow. The gateway is mandatory and has no side door. Capabilities are marked single-use and a second presentation is rejected. Keys sit in hardware. The log is signed by a key the agent cannot read. The claimed tier is 4. Walk the payment again. The agent still holds the delegation token, the agent key, the task credential, and, for a moment, the capability. Inside those lifetimes it presents them for 20 units and, if the scope string is wide enough, for 20,000 units. It can also write the token into context, into a tool argument, into a message to a second agent, and into any evidence field the pipeline retained. Each of those writes is a leak the architecture's own steps made available. The record at every renamed stage stores a pass. The binary question — does this agent have Proof-of-Control? — comes out yes, because the tiers grade the renamed token and the token checked out.

That is the break, and it is not a gap at the edge. Full conformance to the draft reproduces the failure, because the failure is the object the draft told the implementer to issue. The patches change the predicates. They give the agent new places to copy the object. They do not change the issuance.

Three further records sit beside this conclusion and do not repair the issuance. A request that was proved and burned can still arrive at an endpoint that applies a default, an alias, or unsigned state, so the applied effect needs its own published mapping [12]. An unlinkable profile renames the principal as a session pseudonym and still leaves a presentation the agent can carry from step to step [11]. A party that already shares a running endpoint and its ignited allocation shares that allocation until the allocation ends [5]. None of these is a reason to keep a reusable secret as the authority for the next act. They are records that remain after the token has been taken off the path.

## 7. Conclusion

The Standard presents a control architecture fixed by the object it issues. That object, stated in the identity chapter and drawn in the figure, is a signed, short-lived, scoped delegation token from a principal to an agent, with every action supposed to trace to the principal. In practice the figure issues an exposed token into the agent's hands. At every later step the draft renames it — credential, task token, authorization token, approval record, snapshot capability, attested key, peer signature, zero-knowledge presentation, evidence row, tier — and at every later step the agent has an ordinary mechanism by which to copy it or leak it: memory, the call on the wire, the prompt and the context, the approval screen, the message to the next agent, the gateway log, the evidence row it can read back. The patches stack on that exposure and leave the exposure in place. The primitive they avoid is a per-act proof of knowledge, burned before acceptance, on each interactive step and on each direction between two service processes. Until the authority object is that proof, a conformant stack is a conformant relabeling of a fatal issuance, and the agent's copies are conformance working as designed.
